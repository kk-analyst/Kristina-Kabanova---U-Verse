# Architecture & Decisions

## 1. Frontend не определяет факт успешной оплаты

**Контекст:** пользователь возвращается из внешней платёжной формы.

**Решение:** successUrl/failUrl используются для возврата пользователя, но не считаются источником истины. Frontend запрашивает состояние у Backend.

**Причина:** фактический результат операции подтверждается обработанным webhook и сохранённым состоянием U-Verse.

## 2. Webhook как асинхронный источник события

**Решение:** Backend принимает webhook, валидирует его и только после этого изменяет состояние платежа.

**Дополнительные проверки:** подпись, обязательные поля, существование платежа, внешний ID, сумма.

## 3. Polling для T-Bank

**Контекст:** создание платёжного реестра обрабатывается внешней системой асинхронно.

**Решение:** сохраняется correlationId, после чего Backend периодически запрашивает внешний статус. Polling прекращается после финального состояния.

## 4. PATCH для изменения состояния заявки

Изменение состояния ресурса оформляется отдельным PATCH-контрактом. Связанная отправка уведомления выполняется асинхронно.

## 5. Ограничение ответственности Frontend

Бизнес-критичные проверки и изменения состояния выполняются Backend. Frontend отвечает за пользовательский сценарий и отображение результата.
