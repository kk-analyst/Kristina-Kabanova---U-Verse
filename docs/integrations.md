# Integrations

## RaifPay

**Назначение:** проведение оплаты через внешнюю платёжную форму.

```text
Student
  ↓
Frontend U-Verse
  ↓
Backend U-Verse
  ↓
RaifPay payment form
  ↓
Webhook
  ↓
Backend U-Verse
  ↓
DB
```

Ключевое решение: Frontend не устанавливает статус PAID по факту возврата пользователя через successUrl/failUrl. Источник актуального состояния — Backend U-Verse после обработки webhook.

При обработке webhook проверяются структура, обязательные параметры, подпись, существование платежа, внешний ID и сумма.

## T-Bank

**Назначение:** передача платёжного реестра преподавателей и получение его актуального состояния.

```text
Admin
  ↓
U-Verse Backend
  ↓ POST
T-Bank
  ↓ correlationId / PROCESSING
Scheduler / Polling
  ↓ GET
T-Bank
  ↓
U-Verse DB
```

Реестр формируется по расписанию 10-го и 25-го числа месяца. После проверки администратор подтверждает и отправляет реестр.

После принятия запроса T-Bank обрабатывает операцию асинхронно. Backend сохраняет `correlationId`, запускает polling и прекращает его после финального состояния.

## Pruffme

**Назначение:** синхронизация онлайн-занятий U-Verse с внешней системой вебинаров.

Для создания вебинара используется внешний API; в документации также проработаны редактирование вебинара, mapping данных, логирование и обработка ошибок.

Типовые данные интеграции включают идентификатор вебинара, ссылку на комнату и параметры вебинара.

## Kafka

Kafka рассматривается в платёжном/loyalty-контуре как механизм асинхронного обмена событиями.

Важный аналитический аспект — отделение пользовательского HTTP-сценария от фоновой обработки начисления/списания бонусов и связанных операций.

## Unisender

В сценариях найма преподавателей сервис уведомлений используется для асинхронной отправки email-приглашения кандидату после соответствующего изменения статуса заявки.
