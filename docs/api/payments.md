# API — Оплата курсов

## Жизненный цикл платежа

```text
CREATED
   |
   v
WAITING_FOR_PAYMENT
   |                |
 webhook success    cancellation/failure
   v                v
 PAID             CANCELED
```

## POST /orders

Создание заказа перед оплатой.

Backend формирует уникальный идентификатор заказа и сохраняет исходное состояние.

### Business constraints

- стоимость рассчитывается Backend;
- применение промокода выполняется Backend;
- Frontend не является источником истины для итоговой стоимости;
- данные банковской карты не передаются и не хранятся в U-Verse при использовании внешней платёжной формы.

## POST /api/v1/payments/webhook

Приём уведомления от платёжного провайдера.

### Обработка

1. принять запрос;
2. проверить структуру;
3. проверить обязательные поля;
4. проверить подпись;
5. найти платёж;
6. проверить внешний идентификатор;
7. сопоставить сумму webhook с суммой в U-Verse;
8. определить допустимость перехода статуса;
9. сохранить результат;
10. вернуть HTTP 200 при успешно принятом webhook.

Провайдер может повторять доставку webhook, поэтому обработчик должен быть устойчив к повторному сообщению.

## GET /payments/{id}

Получение состояния платежа из данных U-Verse.

Frontend не должен самостоятельно устанавливать PAID после возврата из внешней формы.

### Ошибки

Конкретный набор HTTP-кодов зависит от endpoint-контракта. В проектных сценариях отдельно рассматриваются ошибки валидации, отсутствие платежа и интеграционные ошибки.

## Граница ответственности за данные

Карточные данные остаются за пределами Backend U-Verse при использовании внешней формы оплаты.
